# Second opinion #2: connect-fix bundle

Reviewed offline on 29 October 2026. I read the changed bridge code, daemon, screen app, hotspot helper, deployment scripts and car-session plan. No device was contacted and no runtime source was edited. Tests used copied Java sources with mocked platform calls, extracted daemon logic, and shell scripts operating on synthetic files/fake ADB.

**Verdict: FIX FIRST — repair IP readiness and service startup, make installation fail on errors, and make session-pause state recoverable before spending a car attempt; repair the hotspot helper and toggle path before testing those controls.**

The default 30-second grace and 15-second negotiation deadline are reasonable experiment values. The surrounding lifecycle still has failure paths that those numbers cannot fix.

**Ranked issues**

1. **[P1] “Validated live AP IP” can still advertise the station address or an old boot's pin. Would waste a car attempt: YES.**

   `apIpv4Live()` delegates interface selection to `apInterfaceName()`, which falls back from `ap0` to `swlan0`, `wlan0` and `wlan1` merely because the interface exists. There is no check that the selected interface is an AP. During the station-to-hotspot boot interval, a station `wlan0` address can therefore win over even a correct AP pin. See [BridgeConfig.java:292](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:292) and [BridgeConfig.java:402](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:402).

   If probing returns nothing, `apIpv4Validated()` accepts **any nonempty persistent pin**, without proving it was refreshed this boot or belongs to a currently usable AP. The daemon does not invalidate the pin while AP IPv4 is absent. Thus the null/defer gate often will not activate in precisely the stale-pin case it is intended to protect. See [BridgeConfig.java:384](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:384) and [carplay-boot.sh:98](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:98).

   **Offline reproduction:** the copied actual configuration methods returned a synthetic station address when `ap0` was absent, overriding a synthetic pinned AP address. With no readable interfaces they returned the old pin.

   **Fix:** use this unit's verified AP interface, `ap0`, for this lookup. Treat a pin as usable only alongside a boot-scoped readiness marker published by the privileged daemon after reading the live AP. Invalidate readiness when AP IPv4 disappears. Validate the address format and usable range as well. Preserve the good change that captures `apIp` once and uses that same value for both the packet and its log ([Iap2Session.java:630](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:630)).

2. **[P1] Bridge startup is a one-shot side effect of IP synchronization, with a process check substituting for service health. Would waste a car attempt: YES.**

   Normal cold-boot trace: enable the package and start Watcher → wait for valid AP IPv4 → set the pin → switch/probe the channel → `pgrep` → possibly start BridgeService → set `LAST`. The explicit start is present, so a fresh boot with no matching process and a successful start command can work. However, a failed start still logs `STARTED` and advances `LAST`. Stable AP IPv4 then prevents another attempt. See [carplay-boot.sh:89](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:89) and [carplay-boot.sh:101](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:101).

   A `com.cpbridge` process can also exist without BridgeService: the app contains an activity, and BootReceiver can run and return when its saved `enabled` preference is false. Such a process makes `pgrep -f com.cpbridge` pass and suppresses the only daemon start. See [client/AndroidManifest.xml:29](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/AndroidManifest.xml:29) and [BootReceiver.java:25](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BootReceiver.java:25).

   `pgrep -f` is also a broad regular-expression match on command lines. Whether this unit's toybox excludes particular launcher/ancestor processes cannot be established from the supplied Java and scripts; I would not claim that it always self-matches. An unsupported `pgrep` would return failure and take the start branch, so missing `pgrep` alone is not the startup blocker.

   **Offline reproduction:** executing the actual IP-sync block twice with a fixed AP and an injected service-start failure produced exactly one start attempt. Returning success from the process probe produced zero service starts.

   **Fix:** separate IP synchronization from service supervision. Issue the idempotent foreground-service start after readiness and retry failed starts independently of `LAST`. `BridgeService.onStartCommand()` already guards against starting a second dialer when running ([BridgeService.java:155](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:155)). Preserve service-start exit status/output; log successful startup only after confirmation.

3. **[P1] The installer reboots after failed installs and failed pushes. Would waste a car attempt: YES.**

   `push-fixes.sh` uses `set -uo pipefail`, which reports failing pipeline statuses but does not stop execution. Neither APK install, either script push, nor the init-service grep is checked before reboot. A mixed old/new bundle can consequently be presented as a completed installation. See [push-fixes.sh:12](/Users/saqibsuleman/code/personal/carplay/tools/push-fixes.sh:12), [push-fixes.sh:34](/Users/saqibsuleman/code/personal/carplay/tools/push-fixes.sh:34), and [push-fixes.sh:45](/Users/saqibsuleman/code/personal/carplay/tools/push-fixes.sh:45). The warm installer also ignores installation failure ([install-bridge.sh:8](/Users/saqibsuleman/code/personal/carplay/tools/install-bridge.sh:8), [install-bridge.sh:25](/Users/saqibsuleman/code/personal/carplay/tools/install-bridge.sh:25)).

   **Offline reproduction:** fake ADB failed both installs and both pushes; the real `push-fixes.sh` still attempted reboot and exited zero.

   **Fix:** explicitly abort on every required install, push, ownership/mode and registration check. Verify the staged script bytes against local hashes and verify the installed APK identity/build marker before reboot. Fail if the init service is absent; do not merely print a failed grep. The test should start only after the complete intended bundle is verified.

4. **[P1] Thirty seconds of grace does not guarantee successful-session protection. Would waste a car attempt: YES, especially on a warm install or service restart.**

   `mDialPaused` is populated solely by transient broadcasts to the runtime receiver. Watcher broadcasts on connection transitions and once when initially discovering an existing connection. If Watcher sends PAUSE before the bridge registers its receiver, that state is lost. The daemon starts Watcher before its later bridge-start branch, making this ordering possible for an existing receiver session. A bridge restart also forgets a previous PAUSE. See [carplay-boot.sh:90](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:90), [Watcher.java:116](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/Watcher.java:116), and [BridgeService.java:958](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:958).

   Watcher can spend roughly two minutes retrying callback registration, and can give up; nothing guarantees a callback within 30 seconds. Once the BT link closes and grace expires, an unpaused bridge returns to dialing even if Wi-Fi CarPlay is active. Conversely, a lost RESUME can leave it paused after CarPlay disconnects. See [Watcher.java:47](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/Watcher.java:47), [Watcher.java:95](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/Watcher.java:95), and [BridgeService.java:306](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:306).

   **Fix:** obtain current receiver state on bridge creation and before resuming dialing after grace. A small explicit state-request/reply handshake with Watcher is one option; an authoritative receiver query is stronger. Recover both PAUSE and RESUME state after restarts. Keep the bounded grace as attempt pacing; do not assume it establishes session state. Count the window from the relevant handoff attempt, since each accepted credentials resend currently resets it ([BridgeService.java:112](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:112)).

5. **[P1] Observing the actual AP channel does not prevent advertising the wrong one. Would waste a car attempt: YES if switching to channel 6 fails or has not completed.**

   The daemon publishes `persist.cpbridge.channel=6` before requesting the channel switch. It then reads `CH`, but uses it only in a log message; an empty result or a channel other than 6 still permits bridge startup and advances `LAST`. There is no wait for the AP to report that the switch completed. See [carplay-boot.sh:107](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:107) and [carplay-boot.sh:112](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:112). The bridge prefers the channel property to its live probe ([BridgeConfig.java:329](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:329)).

   **Fix:** verify that the AP is enabled and actually reports the intended supported channel before publishing channel/readiness and allowing handoff. Preserve and check the control reply, retry a failed transition with a bounded deadline, and expose failure explicitly. A log containing the observed channel is useful evidence but is not a readiness gate. Retrying only when the IP changes also cannot recover a failed channel switch on a stable AP address.

6. **[P1] The hotspot helper can destroy build.prop during its attempted recovery. Would waste a car attempt: YES if hotspot flipping is tested; potentially worse than a failed connection.**

   Backup creation is unchecked. A failed `cp` can leave an empty or incomplete backup, after which editing proceeds. If editing/read-back fails, the helper blindly copies that backup over the live file, does not verify restoration, and returns a “no reboot” error. The next eventual boot may then use a damaged property file. See [cp-hotspot-flip.sh:22](/Users/saqibsuleman/code/personal/carplay/tools/cp-hotspot-flip.sh:22) and [cp-hotspot-flip.sh:26](/Users/saqibsuleman/code/personal/carplay/tools/cp-hotspot-flip.sh:26).

   **Offline reproduction:** using a synthetic property file, an injected failed backup that left an empty backup, and an injected failed edit, the actual helper's recovery branch reduced the original file to zero bytes and exited 4. This demonstrates a code path, not a claim that the real filesystem is currently failing.

   **Fix:** abort before editing unless the backup is complete and verified against the original. Check the edit exit status separately; validate a candidate's full contents and metadata before replacing the original. Restore only a known-good backup, and verify restoration. Also preserve the reference script's verity refusal, which this helper omitted ([wireless-mode.sh:100](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/scripts/wireless-mode.sh:100)). `sed -i` changes one character in the resulting contents, but the code does not perform a single-byte in-place write.

   The archived mount table shows `/vendor` normally mounted read-only ([mounts.txt:9](/Users/saqibsuleman/code/personal/carplay/survey/20261026-215704/info/mounts.txt:9)). Returning it to read-only can be appropriate; that command is neither a content-integrity check nor a remedy for an invalid backup, and its failure is ignored. Restore the original mount mode and report failures. `svc power reboot || reboot` is reached from the existing `run_su` path with a root UID check, but the repo does not prove PowerManager acceptance from this exact context. Log and surface a failed reboot rather than consuming the request and assuming success. There is no unconditional reboot loop: requests are removed, and the normal daemon does not create new ones.

7. **[P1] Station mode watches toggle files but never enforces bridge OFF. Would waste a car attempt: YES when testing hotspot OFF/ON.**

   The station-mode branch loops in `handle_triggers()` forever and never reaches the `wl_on=0` force-stop branch. A file request can therefore change the property without stopping a running bridge. More significantly, hotspot OFF with Wireless CarPlay still ON leaves the bridge's saved enabled preference true across reboot; BootReceiver checks that preference alone and can start Bluetooth dialing in station mode. The station daemon neither stops it nor maintains authd. See [carplay-boot.sh:70](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:70), [carplay-boot.sh:81](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:81), [BootReceiver.java:25](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BootReceiver.java:25), and [BridgeService.java:141](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:141).

   **Fix:** enforce the desired runtime state in one common daemon loop: bridge permitted only when wireless mode is active and `wl_on` is enabled. Continue consuming hotspot requests in either mode. Apply the same permission-to-run gate in BootReceiver/service startup. A station-mode `wl_on=1` can remember future intent without immediately starting a wireless bootstrap.

8. **[P2] The toggle mailbox can lose/mix requests, and one control can accidentally request a hotspot reboot. Would waste a car attempt: YES when toggles are exercised.**

   The app truncates and writes the live `toggle.cmd` file directly. The daemon separately opens it to read each key, then deletes it. Polling between open/write/close can consume an empty/partial file; another user write between the two reads or before deletion can be mixed with or deleted by the first request. Writing both keys does not make this exchange atomic. See [MainActivity.java:128](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/MainActivity.java:128) and [carplay-boot.sh:50](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:50).

   Both-key snapshots also turn stale/default UI state into a second command. If property reflection fails, hotspot defaults to OFF; clicking only Wireless CarPlay writes `hotspot=off`, and the daemon can reboot without the hotspot-specific confirmation dialog. See [MainActivity.java:80](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/MainActivity.java:80), [MainActivity.java:116](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/MainActivity.java:116), [MainActivity.java:146](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/MainActivity.java:146), and [carplay-boot.sh:58](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:58). Exceptions/null storage are swallowed and success notes still display, so a failed write is indistinguishable from success.

   **Fix:** submit only the explicitly changed control, with a request ID, through a temporary file renamed after close. Have the daemon atomically claim the file before parsing it once, then acknowledge success/failure. Use an ordered queue or disable a pending control to handle rapid consecutive commands. Represent unreadable state as unknown and prohibit an incidental hotspot request. Surface write/helper failures.

   **Feasibility:** the path itself is credible for primary user 0: the archived device mounts `/data/media` at `/storage/emulated` ([mounts.txt:30](/Users/saqibsuleman/code/personal/carplay/survey/20261026-215704/info/mounts.txt:30)), and the existing collector already uses the same raw external-files path ([collect-device.sh:23](/Users/saqibsuleman/code/personal/carplay/tools/collect-device.sh:23)). Root and permissive SELinux make access plausible; no supplied test proves this new app-to-init exchange. Target SDK 27 and permissive SELinux do not by themselves demonstrate reflection success. Reuse the bridge's `/system/bin/getprop` approach or log reflection failures and verify reads in the real app UID. Neither uncertainty justifies silently defaulting a reboot control.

9. **[P2] “Defer 0x4301” has no resume mechanism. Would waste a car attempt: YES if this gate is reached.**

   On a missing IP the method simply returns. It stores no pending request and registers no readiness callback. Its only call site is receipt of another `0x4300`; `0x4E0E` only resends credentials. Publishing a new IP does not call it, and the new daemon intentionally leaves an existing bridge running. See [Iap2Session.java:258](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:258), [Iap2Session.java:272](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:272), and [Iap2Session.java:630](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:630).

   **Offline reproduction:** the actual session method emitted nothing after an absent IP became available, and sent successfully only when explicitly invoked again. On a quiet NORMAL link the eight-second watchdog generally closes it and permits another attempt, so this is not invariably an infinite deadlock. Ongoing inbound traffic can keep that watchdog alive without producing another `0x4300`; the code provides no progress guarantee. See [Iap2Link.java:348](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:348) and [Iap2Link.java:785](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:785).

   **Fix:** remember the pending availability request and retry sending on readiness, with a finite deadline and cancellation when that link closes. Alternatively, gate the initial BT dial on verified AP readiness. Likelihood is lower on a daemon-only startup after AP readiness, but BootReceiver can start independently before then; no source evidence establishes how often the phone repeats availability.

10. **[P2] The first cold-boot attempt can be erased from the diagnostic capture. Would waste a car attempt: YES, by losing the decisive evidence.**

    The plan reboots, waits for the hotspot, rejoins it, and only then starts collection. Collection immediately clears logcat. An automatic first attempt may already have succeeded or failed by then, and its vendor/Watcher events are removed. The bridge's appended file and daemon log recover some history, but do not recover every vendor receiver event. See [CAR_SESSION_PLAN.md:13](/Users/saqibsuleman/code/personal/carplay/docs/CAR_SESSION_PLAN.md:13) and [collect-device.sh:9](/Users/saqibsuleman/code/personal/carplay/tools/collect-device.sh:9).

    The passive collector also does not initiate a new attempt after changing a knob; a currently paused or connected bridge can yield no new handshake during the collection window. TCP `ESTABLISHED` alone does not establish that the remaining problem is the screen, as the plan suggests ([CAR_SESSION_PLAN.md:28](/Users/saqibsuleman/code/personal/carplay/docs/CAR_SESSION_PLAN.md:28)).

    **Fix:** preserve the preexisting boot log buffer, and preferably arm collection on-device before reboot/bring-up. Give every intended attempt a visible start marker and a defined reconnect trigger while recording. Require receiver-session/callback evidence before diagnosing a display failure. Confirm actual post-boot bundle readiness before spending the next attempt on timeout tuning.

11. **[P2] New elapsed timers use adjustable wall time. Would waste a car attempt: CONDITIONAL, if the device clock changes during boot.**

    Handshake timing, grace and the new negotiation deadline use `System.currentTimeMillis()`. A forward clock correction can prematurely expire a healthy attempt; a backward correction can prolong it. There is no evidence here that a particular bad run experienced a correction. See [BridgeConfig.java:28](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:28), [BridgeService.java:115](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:115), and [Iap2Link.java:747](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:747).

    **Fix:** use one monotonic clock, such as `SystemClock.elapsedRealtime()`, consistently for deadlines and elapsed durations. Keep wall time for human-readable log timestamps.

**What checked out**

- Both explicit entry paths into NEGOTIATING call `enterNegotiating()`: bootstrap and direct FF5A. I found no remaining direct assignment outside that helper ([Iap2Link.java:295](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:295), [Iap2Link.java:405](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:405)). The default 15 seconds includes the roughly four-second initial SYN loop; it is not another mandatory 15-second sleep. Detection precedes the bootstrap entry, so it is not a 15-second deadline for the whole link bring-up.
- Offline tests of the copied actual link code confirmed that an expired negotiation closes/notifies once and that a successfully acknowledged NORMAL link is not closed by the old negotiation timestamp. At the expiry boundary, state transition and timeout decision should share synchronization/recheck state to avoid an ACK racing the close. The timer runs on the bootstrap thread and cannot impose a strict deadline while that thread is blocked in a synchronous write ([Iap2Link.java:228](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:228), [Iap2Link.java:761](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:761)). These limitations do not establish that 15 seconds is too short for the demonstrated normal handshake.
- With no trigger file, `handle_triggers()` returns immediately. The station loop is therefore a sound way to keep listening for hotspot ON, once common bridge-state enforcement is repaired. Writing both keys does not by itself create a reboot loop when the read hotspot value equals the runtime mode.
- The staged bridge APK contains the new validated-IP/grace/deadline markers, and the screen APK contains the toggle markers. This confirms those features are staged locally; it does not verify an installation on the car or byte-for-byte correspondence with every current source file.
- Shell syntax checks passed for the daemon, hotspot helper, device collector, full installer, warm installer and laptop collector. No authentication behavior was changed or exercised against hardware.

**Minimum preparation for the limited visit**

Repair issues 1–5 and preserve the first-boot capture. Either repair issues 6–8 before testing hotspot toggles, or leave those controls out of the connection baseline. Give the deferred request a progress guarantee and switch the new timers to monotonic time. Then run one verified cold-start measurement, one repeat of the successful path, and reserve the remaining attempt for a change selected from complete evidence. The supplied bundle needs these offline fixes before it merits that limited test budget.
