# Third review: round-2 regression check

Reviewed 30 October 2026, offline against the current files. No device was contacted and no runtime sources were edited. Focus: whether the new bundle preserves the previously working cold-boot sequence and whether the specific round-2 fixes hold up.

**The normal cold-boot ordering passes source inspection and mocked regression checks.** The bridge starts after the first valid AP IPv4, failed starts receive later retries, station-mode boot no longer launches the bridge, and the new timer epochs are not mixed. However, the new TCP-based session veto can suppress retries indefinitely, and startup still proceeds after failed IP publication or unknown channel verification. Those are the remaining connection-test blockers. The file-edit helpers and toggle writer also retain concrete failure paths.

**Ranked issues**

1. **[P1] NEW behavior: an arbitrary established TCP connection on local port 7000 can suppress every subsequent BT attempt. Would waste a car attempt: YES.**

   The parser's column indices and hexadecimal comparison are correct: column 1 is local address/port, column 3 is TCP state, `1B58` is 7000, and `01` is ESTABLISHED. IPv6 works because the code uses the last colon. LISTEN and a remote-only port 7000 do not match. See [BridgeConfig.java:434](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:434).

   The semantic test is much broader than “CarPlay receiver connected”: there is no check for receiver ownership, AP address, expected peer, successful protocol setup, or receiver session state. A port probe, an unrelated local connection, or a stalled pre-session connection can satisfy it. The dial loop grants that result an unlimited veto and checks it again every three seconds. This is newly introduced by round 2: [BridgeConfig.java:450](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:450), [BridgeService.java:312](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:312).

   **Offline reproduction:** the actual parser accepted synthetic IPv4 and IPv6 established rows, rejected listeners/remote-only matches, and also accepted an unrelated loopback connection with an unrelated UID. A matching row has no age limit. A stale `mDialPaused=true` also still blocks dialing even after the socket disappears, because the OR short-circuits; this older lost-RESUME problem was not fixed.

   **Fix:** reconcile current vendor receiver state on startup and before redial. The screen app already demonstrates the `getConnectedDevices()` query ([Watcher.java:155](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/Watcher.java:155)). Use TCP state as corroboration or a bounded provisional pause, with a recovery path when no receiver session materializes. Reconcile both stale PAUSE and missed PAUSE. Do not label a socket match authoritative session state.

   **App-UID access:** file-read/parse failure returns false without crashing, which preserves the existing broadcast/grace fallback. Root captures do not prove access from the untrusted app UID; permissive SELinux does not establish every filesystem or process-visibility condition. A denial therefore makes this new protection ineffective rather than preventing the first attempt. Test/read-log that condition once on the unit instead of silently treating “unknown” as a confirmed disconnected state.

2. **[P1] File-edit hardening still permits damaged recovery files and exposes the live file to truncation. Would waste a car attempt: YES if hotspot/RHD edits are exercised.**

   Both scripts now abort before editing when backup creation fails. Candidate generation and the key/length checks also precede the live overwrite. These improvements are real. However, an existing backup is trusted solely because it is nonempty and has the same byte count as the live file. Neither content nor rollback suitability is verified. Restoration is likewise checked only by byte count. See [cp-hotspot-flip.sh:22](/Users/saqibsuleman/code/personal/carplay/tools/cp-hotspot-flip.sh:22), [cp-hotspot-flip.sh:40](/Users/saqibsuleman/code/personal/carplay/tools/cp-hotspot-flip.sh:40), [set-rhd.sh:46](/Users/saqibsuleman/code/personal/carplay/tools/set-rhd.sh:46), and [set-rhd.sh:62](/Users/saqibsuleman/code/personal/carplay/tools/set-rhd.sh:62).

   **Offline reproduction, both device scripts:** injected backup-copy failure now left the original untouched and returned failure. Normal off/on repeat runs succeeded. But an intentionally corrupt existing backup of the correct length passed the guard; after an injected live-write failure, the script restored that corrupt file and its size check accepted it. Neither script rebooted on this detected failure, but the live file was damaged for a later boot.

   The new hotspot helper also replaces `sed -i` with `cat candidate > live`. The shell truncates the original before copying. Candidate validation does not make that copy atomic: interruption during the copy leaves a partial live file and prevents the recovery branch from running. The RHD device script has the same exposure. See [cp-hotspot-flip.sh:39](/Users/saqibsuleman/code/personal/carplay/tools/cp-hotspot-flip.sh:39) and [set-rhd.sh:60](/Users/saqibsuleman/code/personal/carplay/tools/set-rhd.sh:60). **The hotspot helper's explicit truncating live-write path is newly introduced in this round.**

   **Fix:** take a fresh per-operation backup, compare it completely with the current original before editing, and verify restored contents completely. Keep an original archival backup separately if needed. For a single fixed-length character change, a checked write at the exact byte offset avoids truncating the file; alternatively use a verified same-filesystem atomic replacement where the target permits it, preserving metadata. Do not equate a candidate prepared under `/data` with an atomic replacement on `/vendor` or `/system`.

   The size guard is compatible with clean repeated flips because those changes preserve length; the repeat tests passed. It does not establish that an older backup still matches other current settings. Verity refusal is present in both device scripts. Returning an originally read-only mount to read-only is reasonable, but the remount result is ignored and does not validate contents. The code avoids its explicit success reboot after a detected key/length mismatch; it cannot promise that every other byte is intact when it validates only those two properties.

3. **[P1] Startup is decoupled from IP synchronization, but successful configuration publication is not required. Would waste a car attempt: YES on the failure paths.**

   If `setprop persist.cpbridge.ap_ip` fails, the daemon logs that it will retry, then immediately reaches `ensure_bridge()` anyway. If the app cannot read live `ap0`, its fallback remains an unqualified persistent pin. This can reproduce the original wrong-IP handoff despite the correctly neutered BootReceiver. See [carplay-boot.sh:140](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:140), [carplay-boot.sh:153](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:153), and [BridgeConfig.java:387](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:387).

   `ensure_channel6()` retries and reports a known actual channel, but its unknown-channel branch still publishes a guessed 6. It does not report failure to its caller, and `LAST` advances. A stable IP prevents another channel verification. A known unsupported channel is also permitted to proceed. See [carplay-boot.sh:48](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:48), [carplay-boot.sh:59](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:59), and [carplay-boot.sh:146](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:146).

   **Offline reproduction:** the actual main-loop block still started the bridge with pin writes forced to fail. With channel status forced empty, it published channel 6 and started the bridge. These are incomplete fixes; the ordinary successful cold-boot case passed.

   **Fix:** give configuration readiness its own state, separate from both `LAST` and service liveness. Permit the first service start only after a current pin is successfully published/read back and the AP's actual usable channel is verified. Return failure on unknown channel, retry readiness independently of IP change, and keep service-start retries independent once ready. During subsequent AP disappearance or replacement, invalidate the old published readiness rather than continuing to authorize a stale pin. This preserves the intended separation without reintroducing force-stops for every IP update.

4. **[P2] The hardened RHD device script may never reach the device, yet its caller executes the old copy and can reboot. Would waste a car attempt: YES if RHD is tested.**

   `set-rhd.sh` ignores failure of the push to its fixed remote script path, then executes whatever is already at that path. It selects reboot from the output prefix rather than also requiring a successful remote exit status. See [set-rhd.sh:70](/Users/saqibsuleman/code/personal/carplay/tools/set-rhd.sh:70).

   **Offline reproduction:** fake ADB rejected that push and returned an `OK` result from a previously staged script. The real caller still executed that path, attempted reboot and exited zero. Thus the newly reviewed safety checks are not guaranteed to be the checks actually executed.

   **Fix:** abort on failed push, verify the staged script, and require both a successful remote exit status and the expected exact success marker. This is a caller gap alongside the round-2 hardening. Keep this optional `/system` edit out of the connection baseline.

5. **[P2] The atomic toggle writer contains a direct-write fallback. Would waste a car attempt: YES if rename fails while a toggle is tested.**

   The successful path writes, syncs and closes a temporary file in the same directory before renaming it to `toggle.cmd`. That is the appropriate atomic-publication pattern for this layout. But `renameTo` failure opens and truncates `toggle.cmd` directly, writes it, and returns true. The daemon can read an empty or partially written request in that branch. See [MainActivity.java:145](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/MainActivity.java:145) and [MainActivity.java:157](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/MainActivity.java:157).

   **Fix:** return false on failed rename and surface the existing failure UI. Do not silently downgrade to direct publication. Same-directory replacement should be exercised on the actual app storage once; the source alone does not certify this unit's Java/filesystem implementation. The fallback makes a failure to replace unsafe even when the normal rename operation works correctly.

   The only-changed-key fix does remove the previously identified accidental reboot path: the Wireless CarPlay click writes only `wl_on`, and hotspot intent is emitted by the confirmed hotspot click ([MainActivity.java:80](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/MainActivity.java:80), [MainActivity.java:95](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/MainActivity.java:95)). The successful rename path publishes complete bytes. A daemon reading the mailbox twice can still read different complete generations, then delete a newer request; atomic publication does not atomically consume the mailbox ([carplay-boot.sh:84](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:84)).

6. **[P2] The grace timestamp is monotonic, but the wait consuming its remaining duration still uses wall time. Would waste a car attempt: YES if wall time moves backward during that wait.**

   `mQuietDialUntilMs` is correctly written and subtracted using `elapsedRealtime()`. Its remaining *duration* is passed to `waitDial`, which converts it into `currentTimeMillis() + ms` and loops against that wall deadline. A backward clock correction can therefore extend the actual wait. See [BridgeService.java:320](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:320) and [BridgeService.java:903](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:903).

   **Fix:** make that relative waiting helper monotonic too, or return to the outer monotonic state check after a bounded wait. This is a retained limitation, not a direct comparison between incompatible epochs and not a newly broken watchdog. There is no supplied evidence that a clock correction caused a particular failed run; it need not trigger a broader watchdog rewrite for this test.

**Cold-boot regression trace and verified fixes**

With `ro.atc.carplay.wireless=1` and `wl_on` enabled, the current ordering is:

1. Init launches the daemon using the existing `late_start`, `u:r:init:s0`, `oneshot` declaration ([carplay-wireless.rc:15](/Users/saqibsuleman/code/personal/carplay/tools/carplay-wireless.rc:15)).
2. The daemon enables the bridge package and starts Watcher, then checks/spawns authd ([carplay-boot.sh:124](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:124)).
3. Each iteration probes `ap0`; no AP IPv4 means no daemon service start. On the first observed valid IP it publishes the pin/credentials and performs channel switching/verification, then calls `ensure_bridge` ([carplay-boot.sh:133](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:133)).
4. `BRIDGE_ON=0` guarantees the first call attempts a start regardless of `n`. When `n=0`, the OR condition runs the body once; it does not cause two starts. Later calls at `n % 10 == 0` re-ensure the service. Existing `onStartCommand` avoids spawning another worker when `mRunning` is true ([carplay-boot.sh:70](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:70), [BridgeService.java:156](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:156)).

Mocked executions of the current functions/main loop produced:

| Scenario | Bridge start calls |
|---|---|
| AP ready immediately | `n=0`, then `n=10` |
| AP appears at iteration 4 | `n=4`, then `n=10` |
| First service-start command fails | `n=0`, then retry at `n=10` |
| Pin publication fails | Still starts at `n=0` — issue 3 |
| Channel status unavailable | Publishes guessed 6 and starts — issue 3 |

The retry interval is roughly 30 seconds plus command runtime, not a strict timer. `BRIDGE_ON` is set even on a failed start, so the first failure waits for the periodic retry; it is no longer hidden forever by a stable `LAST`.

BootReceiver now only initializes logging and records the saved preference; it contains no foreground-service start ([BootReceiver.java:25](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BootReceiver.java:25)). This removes its premature/station-mode automatic starts. The station branch force-stops once and continues consuming hotspot requests, which is consistent with that change ([carplay-boot.sh:104](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:104)). Manual installer/kick scripts can still start the service; “daemon only starter” accurately describes the automatic boot design.

The daemon is now a single automatic-start dependency. If init does not launch it, or it exits and leaves its `/dev` directory lock behind, BootReceiver provides no rescue. The oneshot service also does not supervise a terminated daemon. These mechanisms already existed; removing the fallback makes their verification essential rather than demonstrating that a normal boot is broken. `push-fixes.sh` checks files and an init-file entry, which does not prove the init service actually ran. Before labeling a test a connection failure, require the current boot's daemon start/ensure logs and the bridge-created marker. The archived service declaration and prior daemon logs support feasibility, not a guarantee about the currently installed image.

**Clock audit:** no new deadline subtracts a wall timestamp from an elapsed timestamp. Handshake epoch and elapsed duration both use `elapsedRealtime` ([BridgeConfig.java:35](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:35)); grace assignment/subtraction do too. `mNegotiatingSinceMs` uses elapsed time, and `timerLoop` compares it with a separate `enow`. `mLastRxAt`, `mLastSynSentAt` and pending retransmission times remain on wall time and are compared with `now`. The intended isolation holds ([Iap2Link.java:748](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:748), [Iap2Link.java:760](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:760)). A copied-source test with an elapsed epoch far from wall time did not prematurely expire negotiation; advancing only elapsed time beyond the deadline closed it once. Issue 6 concerns the downstream wait's behavior, not epoch arithmetic.

**Deployment/capture:** fake-ADB install failure and push failure now made `push-fixes.sh` exit 1 without reboot; the mocked success case rebooted. The warm installer also checks install success. File existence/init-entry checks are useful but do not verify hashes, final modes or runtime service state ([push-fixes.sh:35](/Users/saqibsuleman/code/personal/carplay/tools/push-fixes.sh:35), [push-fixes.sh:53](/Users/saqibsuleman/code/personal/carplay/tools/push-fixes.sh:53), [install-bridge.sh:25](/Users/saqibsuleman/code/personal/carplay/tools/install-bridge.sh:25)). `logcat-pre.txt` is saved before clearing; this repairs the main earlier capture-loss issue, though there remains a short snapshot-to-clear gap and `timeline.txt` only summarizes the post-clear file. Inspect the pre-file as the updated plan directs ([collect-device.sh:12](/Users/saqibsuleman/code/personal/carplay/tools/collect-device.sh:12), [collect-device.sh:30](/Users/saqibsuleman/code/personal/carplay/tools/collect-device.sh:30)).

Shell syntax checks passed for the daemon, hotspot helper, collector, both installers, RHD caller and extracted RHD device script. Java checks used copied current protocol/configuration sources with mocked Android clock/command boundaries. These tests do not establish app-UID proc access, real filesystem rename behavior, or actual hardware connection timing.

**The two explicitly deferred residuals**

- **Rapid double-toggle:** acceptable to leave out of this limited connection experiment if requests are deliberately serialized and application is confirmed before another click. It remains unsuitable as a reliable general-purpose mailbox. Remove the direct-write fallback first; no special rapid gesture is needed to reach that separate failure path. Atomic claiming plus request IDs/acknowledgments is the later consumption fix.
- **Deferred `0x4301` without explicit resume:** acceptable for a controlled first cold-boot test **after issue 3 is fixed**, because the daemon then establishes a current pin before starting the bridge. It remains a liveness defect if reached: only another availability message invokes the sender, and ongoing inbound traffic can keep the NORMAL watchdog alive without providing that message. Treat `DEFERRED` in the test as a stop-and-capture condition, not a reason to spend another attempt shortening grace. An eventual general fix should remember the pending request and retry on readiness ([Iap2Session.java:258](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:258), [Iap2Session.java:630](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:630)).

**Verdict: FIX FIRST for the new unbounded TCP pause and failed-readiness startup; then GO for a captured cold-boot connection baseline. Defer hotspot/RHD edits until their write/recovery and staging gaps are repaired.**
