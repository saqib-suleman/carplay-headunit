# Wireless CarPlay second opinion

Reviewed 29 October 2026, entirely offline. This review uses the local source, decompiled vendor Java, supplied binaries, and existing captures. No car connection or deployment was attempted. Existing captures establish what happened in those runs; they do not establish which APK, properties, or daemon revision is installed today.

**Recommendation: retain the custom Bluetooth bootstrap for now, but replace its startup/retry orchestration. Do not commit to replacing it with the vendor HAL, and do not spoof a USB connection.** There are concrete lifecycle defects that can explain minutes of delay and indefinite failure. There is not sufficient evidence that the vendor firmware contains a usable replacement wireless bootstrap. The design needs a readiness and session coordinator, rather than independent startup paths and optimistic handoff timers.

The strongest finding is a two-minute retry suppression triggered by *sending credentials*, before connection success. One saved run shows RFCOMM-to-session-request taking 3.409 seconds, followed by the watchdog and about 110 seconds of suppressed retries. That is a much stronger explanation for minute-scale gaps than slow authentication or the daemon's three-second poll.

**Ranked hypotheses**

The ranks combine evidence strength and explanatory value. “Confirmed defect” means the behavior exists in source; its contribution to every reported 5–8 minute connection still needs a complete cold-boot trace. Test lines below are for the next visit, from a root shell on the unit. Keep captured output local: existing logs can contain device identity and hotspot credentials.

1. **Premature two-minute retry suppression amplifies failed handoffs. Confirmed in source and a capture; highest confidence for minute-scale gaps.**

   `sendWifiConfiguration()` invokes `onWifiSent()` after `0x5703`. That callback sets `mQuietDialUntilMs = now + sessionQuietMs()`. The default is 120,000 ms, and the dial loop honors it whenever the link has closed. There is no receiver-success check at this point. Every accepted credentials resend can extend the deadline, including the post-transport resend. See [Iap2Session.java:600](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:600), [BridgeService.java:112](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:112), [BridgeConfig.java:123](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:123), and [BridgeService.java:306](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:306).

   The existing capture actually records the eight-second watchdog followed by “post-handoff quiet: holding re-dial ~110s”; see [10_logcat_full.txt:2818](/Users/saqibsuleman/code/personal/carplay/wireless-data/20261028-222218/10_logcat_full.txt:2818) and [10_logcat_full.txt:2826](/Users/saqibsuleman/code/personal/carplay/wireless-data/20261028-222218/10_logcat_full.txt:2826). The “re-dialing immediately” message in the close handler is therefore misleading: waking the dialer does not bypass the quiet-state check ([BridgeService.java:879](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:879)).

   **Confirm:** `logcat -v epoch | grep -E 'SENT 0x5703|SENT 0x4301|post-handoff quiet|LINK WATCHDOG|PAUSE_DIAL|RESUME_DIAL'`

   **Fix implied:** treat credentials sent as an attempt, with a bounded handoff deadline. Suppress bootstrap retries for an established receiver session using authoritative connection state. On failed handoff, retry promptly with bounded backoff. Setting `persist.cpbridge.session_quiet_ms=0` is a useful controlled experiment, but continuous redial after success is not the final design. Preserve the existing connected-session pause, and make it recoverable after either app restarts.

2. **Bluetooth starts before a coherent AP/receiver configuration is ready. Confirmed missing readiness gate; likely source of first-attempt failure.**

   `BootReceiver` can start the bridge at `BOOT_COMPLETED`, based on a saved enabled preference. The dialer waits for the auth socket, but does not wait for AP IPv4, verified channel, DHCP readiness, or receiver readiness. See [BootReceiver.java:22](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BootReceiver.java:22) and [BridgeService.java:285](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:285).

   `BridgeConfig.apIpv4()` prefers any nonempty persistent property over the live interface. If no property or live address is available, it falls back to a guessed address. The daemon leaves the persistent property untouched while AP IPv4 is absent. Thus a previous boot's address can be advertised before this boot's hotspot exists. `0x4301` is sent on receipt of `0x4300` without a readiness check. See [BridgeConfig.java:343](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:343), [carplay-boot.sh:69](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:69), and [Iap2Session.java:619](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:619).

   The vendor enable chain has additional dependencies after the AP starts. An AP IPv4 is insufficient evidence that the receiver is ready. Conversely, port 7000 was already listening before the saved October 28 attempt, so “no listener” cannot explain every failure: [03_port7000_before.txt:1](/Users/saqibsuleman/code/personal/carplay/wireless-data/20261028-222218/03_port7000_before.txt:1) contains TCP state `0A` on local port `1B58` (7000).

   **Confirm:** `while true; do cat /proc/uptime; ip -4 -o addr show ap0; grep -i ':1B58 ' /proc/net/tcp /proc/net/tcp6; sleep 1; done`

   Compare this with timestamped `SENT 0x4301` and the daemon log. The decisive event is an attempt before readiness, or an advertised IP different from the contemporaneous interface address.

   **Fix implied:** publish one validated configuration snapshot only after the AP, tethering, actual channel, receiver identity and listener are ready. Defer bootstrap or at least credentials/session messages until then. Invalidate readiness when the AP disappears. Read privileged network state in a small privileged coordinator if the app cannot read it reliably; merely clearing the override still leaves the guessed-address fallback.

3. **The daemon can interrupt an active handshake and advertise an unverified channel. Confirmed defects; frequency-dependent impact.**

   Despite its “No restart races” comment, the implementation runs `am force-stop com.cpbridge` followed by a foreground-service start. `LAST` begins empty, so the first observed IPv4 triggers this even if the bridge already has an active RFCOMM session. Every subsequently observed different IPv4 does the same. See [carplay-boot.sh:6](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:6), [carplay-boot.sh:47](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:47), and [carplay-boot.sh:72](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:72).

   It pins advertised channel 6 before requesting `chan_switch`, discards the command output, does not verify the resulting channel, then immediately restarts the bridge. Failure to change channel still leads to advertising 6 because the property overrides live probing. See [carplay-boot.sh:78](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:78) and [BridgeConfig.java:296](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeConfig.java:296). The interactive helper at least waits and reads status after its switch: [apfix.sh:34](/Users/saqibsuleman/code/personal/carplay/tools/apfix.sh:34).

   This is **not** a restart every three seconds: it requires a valid address different from `LAST`. A random address once per boot implies one initial kick, not continuous churn. Also, disappearance followed by the *same* IP does not trigger a new kick; credentials/channel changes without an IP change are missed. `run_su` errors are hidden, yet `LAST` advances anyway, so a failed service start may not be retried. See [carplay-boot.sh:45](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:45) and [carplay-boot.sh:81](/Users/saqibsuleman/code/personal/carplay/tools/carplay-boot.sh:81).

   **Confirm:** `tail -F /data/local/tmp/carplay-boot.log`

   Correlate each `PINNED ... kicked bridge` with the bridge PID/start marker and handshake milestones; separately check actual `hostapd_cli status` after the switch. Stable IP plus no further kicks would demote restart churn as the explanation for later minute-scale gaps.

   **Fix implied:** configure the AP channel before advertising it, verify actual status, and notify a running coordinator of network-generation changes. Cancel only an attempt using an invalidated configuration; start a new attempt once readiness is restored. Do not force-stop the whole app just to refresh a property that is already read per message. Supervise startup success independently of whether the IP changed.

4. **Failed SYN negotiation can hold the only active-link slot indefinitely. Confirmed unbounded failure path; strong reliability explanation if observed.**

   After eight initial SYN attempts at 500 ms, failure merely enters the timer loop. That loop resends SYN every second without an overall negotiation deadline. The no-RX watchdog applies only to `STATE_NORMAL`. Meanwhile the dialer sees `mLink != null` and waits instead of trying again. An open RFCOMM socket with a silent/non-negotiating peer can therefore block reconnect indefinitely. See [Iap2Link.java:292](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:292), [Iap2Link.java:743](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:743), [BridgeService.java:306](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:306), and [BridgeService.java:818](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:818).

   **Confirm:** `logcat -v epoch | grep -E 'SYN NOT ACKED|retry while NEGOTIATING|state=NEGOTIATING|NEGOTIATION COMPLETE|DIAL |link dead'`

   **Fix implied:** give detect, negotiation, identification, authentication and handoff explicit overall deadlines. On negotiation expiry, close the owned socket, clear the active attempt exactly once, and schedule a bounded retry. Increasing the NORMAL watchdog does not repair this path.

5. **Authentication can collide with the shorter link watchdog; missing authd can also add two minutes before dialing. Conditional defects, but not slow in the captured healthy exchange.**

   The initial dialer auth-socket wait is up to 120 seconds. Each auth request can then spend up to 20 seconds connecting to the daemon, and has a 20-second socket-read timeout. The daemon's job deadline defaults to 15 seconds. These are failure budgets, not delays paid on successful calls. See [BridgeService.java:289](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:289), [AuthDaemonClient.java:148](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/AuthDaemonClient.java:148), [Iap2Constants.java:288](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Constants.java:288), and [authd.c:87](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/authd/src/authd.c:87).

   Auth processing runs synchronously in the RFCOMM receive callback. A slow certificate/signing operation, or even the optional serial-number diagnostic after the certificate, can stall further reads while the separate NORMAL watchdog fires after eight seconds without RX. See [Iap2Link.java:629](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:629), [Iap2Session.java:474](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:474), [Iap2Session.java:502](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Session.java:502), and [Iap2Link.java:762](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Link.java:762). A failed auth client also latches unavailable for that session ([AuthDaemonClient.java:65](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/AuthDaemonClient.java:65)).

   **Confirm:** `logcat -v epoch | grep -E 'waiting for auth daemon|absent after 120s|AUTH daemon|AUTH REJECTED|AUTH SUCCEEDED|LINK WATCHDOG'`

   **Fix implied:** make genuine-chip certificate/sign readiness a prerequisite, keep auth work off the receive thread, and coordinate protocol deadlines with outstanding auth jobs. Move optional serial diagnostics out of the handshake. Abort and retry cleanly on genuine-auth failure instead of sending empty/zero placeholders. Preserve the genuine MFi implementation.

6. **Vendor receiver startup or its outgoing control connection may be missing, but “set the native iAP2 bit” is not an established cure. Plausible integration gap; lower confidence.**

   The plugin subscribes to USB iAP2 events, and sets the native flag true only on USB-connected. The bridge emits no corresponding vendor event. That gap is real. See [vendor plugin/a.java:33](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/plugin/a.java:33) and [vendor plugin/a.java:253](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/plugin/a.java:253).

   However, the vendor service explicitly accepts `CARPLAY_SESSION_CONNECTED` even when iAP2 was not reported connected, logging “iap not connected” and advancing its connection state. That weakens the claim that the flag universally prevents incoming wireless sessions: [vendor service/v.java:80](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/v.java:80). The native binary contains the reported wait/connect strings and control-client symbols, but its callback is in an encrypted section in the supplied file. Strings do not establish the full branch behavior, retry timing, or whether that branch is necessary when the phone initiates the connection.

   **Confirm:** `logcat -v epoch | grep -E 'CarplayPluginAdapter|CARPLAY_PLUGIN_|NET_IFACE_|iap2 session|CarPlayControlClientConnect|AirPlay session|CARPLAY_SESSION_'`

   **Fix implied:** first determine whether the failure is listener startup, Wi-Fi/DHCP/TCP, incoming receiver negotiation, or the vendor's outgoing control request. If a controlled build proves that outgoing control is blocked solely by missing authenticated-BT state, add a real authenticated-BT lifecycle notification to the vendor adapter and test discovery replay. Faking a USB event risks driving the USB-specific connection-state branches and does not supply the HAL with a transport.

7. **Wrong-peer scans and missing screen callbacks can add delay or make success appear absent. Secondary checks.**

   Dial attempts are serial: nominal budgets are 3.5 seconds for socket creation, 3.5 for connect, 2.5 for channel-1 fallback, plus five seconds between failed cycles. A configured peer MAC that does not match falls back to normal candidate ordering rather than enforcing “only this phone.” See [Iap2Constants.java:37](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/Iap2Constants.java:37), [BridgeService.java:334](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:334), and [BridgeService.java:375](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:375).

   Separately, Watcher retries callback registration every two seconds, up to 60 scheduled retries, then gives up. This does not delay network establishment, but can delay or prevent showing a successful session. Its PAUSE/RESUME broadcasts are also transient; the bridge does not query current receiver state when recreated. See [Watcher.java:47](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/Watcher.java:47), [Watcher.java:95](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/carplay-screen/src/app/carplayscreen/Watcher.java:95), and [BridgeService.java:958](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/src/com/cpbridge/BridgeService.java:958).

   **Confirm:** `logcat -v epoch | grep -E 'dial cycle:|NO MATCH|SDP resolution timed out|connect timed out|CarPlayScreen|CARPLAY_SESSION_CONNECTED'`

   **Fix implied:** fail clearly on an unmatched explicitly configured peer, distinguish receiver-connected from screen-visible timing, and make callback registration and connection-state resynchronization resilient to service restarts.

**Where the time actually goes**

The successful local path is not a mandatory five-minute sequence. The important distinction is between parallel startup, conditional failure budgets, and waits deliberately serialized between attempts.

| Stage | Code behavior and time contribution |
|---|---|
| Android boot / vendor enable | Unmeasured for the reported bad boots. The reference author reports about a minute of boot time, not a guaranteed timer in this code. |
| Vendor subsystem chain | USB NCM → Bluetooth → AP → iAP2 subsystem → NSD adapter → plugin if a tracked interface has a hardware address. Failure timers are 1, 9, 5, 2, 2 and 10 seconds respectively; success events cancel them. They are not mandatory sleeps to add together. See [service/f.java:37](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/f.java:37). |
| Receiver interface gating | The predicate checks interface hardware addresses, not complete IPv4/DHCP readiness. Later interface events can start the plugin. See [service/i.java:214](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/i.java:214) and [service/d.java:43](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/d.java:43). |
| Daemon and bridge startup | `late_start` daemon and app boot startup can overlap vendor bring-up. The daemon waits indirectly for AP IPv4 before its kick; the app boot path can dial earlier. Polling adds roughly 0–3 seconds after IPv4 appears, plus command runtime; commands are not all bounded. |
| Authd readiness | Up to 120 seconds before the dial loop if unavailable. Usually overlaps vendor/AP startup; do not simply add it to AP startup time. |
| RFCOMM / link / auth | Serial per attempt. Failed peers cost nominally up to 9.5 seconds each, then five seconds per failed cycle. Silent version detection exits after about 15 probes, unmatched incoming bytes after five; initial SYN waits about four seconds, followed by the unbounded retry defect. Auth time is measured below. | Wi-Fi credentials / session request | Event-driven responses; no readiness barrier. The two-minute quiet deadline starts at credentials sent and runs concurrently with handoff. It becomes a serial retry delay only if the handoff fails and another bootstrap is needed. |
| Phone association / DHCP / receiver handshake | Not timed end-to-end in the cited capture. Must be observed before assigning the residual delay to iOS discovery/backoff. |
| Display | Usually callback-driven; the registration retry window is separate from transport connection. |

**AP address and startup design**

The vendor adapter calls Android `ConnectivityManager.startTethering(0, true, ...)`; its AP-start event comes from AP state 13. It does not assign an IPv4 address in the inspected Java. See [c/e.java:58](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/c/e.java:58) and [c/h.java:20](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/c/h.java:20). Address randomization is reported by the reference author ([GUIDE.md:281](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/docs/GUIDE.md:281)); the implementation choosing that address is not present in the inspected decompiled sources. I cannot establish its precise algorithm or why a particular boot takes minutes from these files.

There is no multi-minute deliberate AP-start sleep in that adapter: the enable state machine expects AP startup within five seconds, after earlier prerequisites. Long AP absence calls for tracing vendor enable timing, tethering failures, framework/network readiness and teardown. Failure transitions can themselves stop AP/BT: [service/f.java:94](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/f.java:94), [service/e.java:100](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/e.java:100).

An early, stable AP would help if late AP startup is demonstrated, but **a fixed IP is optional, not the prerequisite for reliability**. A dynamic address is workable when each attempt uses a current, validated snapshot. A real fixed-address implementation must coordinate the tether interface, DHCP subnet/router and routes in the component owning tethering; setting `persist.cpbridge.ap_ip` or adding a competing `ip addr` command does not accomplish that. The current daemon does not start the hotspot at all—it waits for the vendor to do so. A fixed address alone does not repair retry suppression, unbounded SYN negotiation, auth/watchdog conflict, or receiver state.

**What driving the vendor path would actually mean**

The service's enable entry sends `USER_TURN_ON` to the state machine, whose disabled state transitions to enabling. The wireless branch is selected from the read-only property at class initialization. This machinery already owns BT/AP/receiver bring-up in the present architecture: [CarplayService.java:50](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/CarplayService.java:50), [service/c.java:25](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/c.java:25), [service/a.java:23](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/service/a.java:23). We have replaced the Bluetooth protocol bootstrap, not the entire vendor enable path.

`IAP2_STARTED` is subsystem readiness: the adapter has called `createCarplay`, set configuration and emitted a start event. It does not mean an authenticated phone connection exists. Actual transport-specific connection events arrive separately through `IIAPClient.onConnectStatusChanged`, then map to USB/BT/CarPlay event families. See [a/a.java:48](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/a/a.java:48), [a/a.java:118](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/a/a.java:118), [a/b.java:49](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/a/b.java:49), and [a/a.java:178](/Users/saqibsuleman/code/personal/carplay/decompiled/CarplayService/sources/com/autochips/carplay/a/a.java:178).

The reference notes explicitly report a NULL client transport, `connectTransport` returning `0x80000000`, no reads from the supplied transport, and stub Wi-Fi configuration: [PHASE_B.md:5](/Users/saqibsuleman/code/personal/carplay/headunit-carplay-ref/client/PHASE_B.md:5). Treat the broad HAL diagnosis as the author's recorded finding, not fresh proof of every native path. A supplemental local binary check does support one narrow point: the exported `IAP2Control::setWiFiConfigInfo` symbol in `survey/20261026-215704/iap/libiapimpl.so` resolves to `0xae2b8`, which is `mov w0, wzr; ret`—a no-op returning zero. That does not prove every Bluetooth entry point is unusable, but it undermines “just feed the vendor transport” as a demonstrated minimal fix.

The smallest justified change is therefore a coordinator around the working custom bootstrap and existing vendor receiver. If hypothesis 6 is subsequently confirmed, the smallest *vendor integration experiment* is to subscribe the plugin adapter to genuine authenticated BT connect/disconnect/failure state and forward that lifecycle to its native flag. It also needs a privileged, authenticated IPC path from the bridge, correct device/session lifetime, and a test of whether already-discovered controllers are reconsidered. This supplies status; it does not magically implement the missing HAL transport or wireless credential messages. Its speed benefit is conditional, not established by the present source.

The decompiled files contain obvious reconstruction artifacts, including uninitialized locals in some switch branches. The event sequence, explicit calls and constants are useful evidence; impossible-looking Java should not be interpreted literally as a proven vendor runtime defect.

**A2DP is an integration clue, not proof that wireless audio is impossible**

There is explicit vendor Bluetooth teardown code. If `ro.atc.carplay.disable_bt` is true, a session-connected event can request adapter shutdown.
